# Witnessed history experiment v1

Issue #23, based on PR #29 at cfef0bfbe414c21770c50b7cb2af4bfd3b74789f. Tested source b5bb17e523d17e66418012b5de97915ce2da43ef. This opt-in Linux fixture wraps the existing SQLite claim and consume operations. The default broker still uses its existing store.

The trusted controller enrolls a fresh database with a random lineage identifier. An external witness directory holds a namespace, generation, SHA-256 of the complete database image, device and inode. A directory lock serializes participating processes. For each claim the controller checks the live checkpoint, copies the verified image into a private directory, invokes the existing SQLite transaction there, syncs the image, advances and syncs the witness, then installs and syncs the live image before returning success. A trusted operator can rebind a backup only if its full digest matches the current witness. Each successful recovery advances the generation.

| Fixture | Expected and observed |
| --- | --- |
| Fresh enrollment | First claim and consumption succeeded. Repeated claim refused. |
| Missing database, then current backup | Ordinary consumption refused. Explicit restore succeeded. Used token refused and fresh claim succeeded. |
| Earlier valid SQLite snapshot | Ordinary claim and explicit recovery both refused. |
| Deleted claim rows | Fresh claim refused. |
| Changed namespace or substituted identical file | Ordinary claim refused in each case. |
| Missing or malformed witness | Fresh claim refused. |
| Process death during restore | Child exited 77 between witness commit and file installation. Fresh claim refused. Retrying with the matching backup succeeded and preserved the replay refusal. |

The focused suite passed all eight tests at the published source. The first development run produced six passes and two failures because the exception handler translated a known replay into a generic storage refusal. The repair preserves both refusal types. The combined local suite passed 344 with one skip for unavailable Landlock ABI. Historical v1 regenerated byte-identical failed results. The v3 instrument passed ten checks and retained its 9/3484 false allows. The v4 instrument passed 16 checks and verified the recorded invalid predecessor and both passing artifacts. No historical input or result was edited.

## Reproduce

From a full clone on Linux, use a fresh virtual environment and the repository's requirements-dev.txt and requirements-build.txt. Local measurements used Linux 6.18.57 x86_64, Python 3.12.14, SQLite 3.53.1 and pytest 8.3.5.

```sh
python -m pytest -q tests/test_history_continuity_v1.py
python -m pytest -q -rs --ignore=benchmarks/replay_v3/test_instrument.py --ignore=tests/test_replay_v4_instrument.py
bash scripts/verify_historical_authority.sh
bash scripts/verify_v4_history.sh
```

## Trust and recovery limits

The synthetic witness stands in for a separately protected, durable monotonic service. Its filesystem permissions, path identity, controller, provisioning identity and single enrollment are trusted. Someone able to rewind both files can rewind this experiment. All writers must honor the witness lock. The model permits offline damage to the live image between operations and excludes hostile concurrent changes to controller paths or staging files. Backup authentication comes from the trusted checkpoint digest. Operator authentication is assumed. The checkpoint authenticates byte-exact images, so a logically equivalent re-export can be refused.

A failure after witness advancement can burn a claim. Recovery requires the exact witnessed bytes. If those bytes have also been lost, the controller must keep refusing. Issue #26 covers reconciliation with an external effect. These tests use synthetic claims and perform no external effects. Process termination was exercised; host power loss, hardware monotonic storage, distributed writers and throughput at scale were outside this measurement. Each claim copies and hashes a full SQLite image.
